# hypetype — интерфейс типографа (`TYPOGRAPH_UI_PLAN.md`)

ТЗ на проектирование и реализацию **UI настроек типографа**. Экспериментальная работа —
в отдельной ветке (напр. `typograph-ui`), `main` не трогаем, пока не понравится.

Это документ-посев для нового диалога: прочитать целиком, затем идти по шагам.

---

## 0. Контекст и мотивация

- Типограф-**движок** у hypetype уже есть, покрыт тестами, идемпотентен (`Typograph.swift`,
  правила — в `TYPOGRAPH.md`, общий источник правды с Windows). Не хватает только **UI настроек**.
- Появился конкурент (известный дизайн-блогер): mac-only, закрытый, без опенсорса,
  движок менее предсказуем, а UI — **простыня из ~80 чекбоксов** одним экраном (см. `bad_typograph.pdf`).
  Мощно на скриншоте, невыносимо в работе. Нам нельзя отдавать рынок сырому закрытому решению.
- Наши козыри: **предсказуемость (тесты, идемпотентность), опенсорс, кросс-платформа,
  переносимый конфиг**.

## 1. Анти-паттерны конкурента (чего НЕ делаем)

- ❌ Вываливать все правила одним длинным списком — когнитивная перегрузка.
- ❌ Дублировать примеры текстом у каждого пункта (шум).
- ❌ Прятать пресеты над стеной галочек — до них никто не долистывает осознанно.
- ❌ Нет живого предпросмотра «до/после» — а это главное, ради чего типограф открывают.

## 2. Наши принципы (UX)

1. **Пресет-first.** Крупные пресеты сверху: «Сам решай / Базовый / Стандартный / Продвинутый»
   + «Кастомный». 90% пользователей выбирают пресет и не лезут в детали.
2. **Сильная композиция без повторов.** Никаких повторяющихся примеров в тексте —
   **примеры показываются в подсказке по наведению** (hover-тултип) на правило.
3. **Компактная матрица вместо простыни.** Правила группируются в таблицу-матрицу
   (пример из эскиза: «Неразрывный пробел» × [после / 1-буквенных / 2-х / 3-х буквенных] ×
   [предлоги / союзы / частицы / местоимения] — галочками). Плотно, обозримо, без воды.
4. **Живой предпросмотр «до → после»** на тестовом тексте — ключевой «вау» и аргумент доверия.
   (Точное место/форму уточнить — см. открытые вопросы.)
5. **Переносимость.** Настройки типографа хранятся в общем `config.ini` (секция `[Typograph]`),
   как раскладка — переезжают между устройствами и между macOS/Windows. Фича, которой у
   конкурента быть не может.
6. **Исключения** — стоп-лист слов, которые не трогать (единственная ценная идея у конкурента).

## 3. Как открывается

- Из интерфейса редактора hypetype — **по клику на клавишу ⌫ / «ТИПОГРАФ»** (она физически
  Backspace, и на ней же висит хоткей типографа — логичная точка входа).
- **Ширину окна оставляем** как у редактора-клавиатуры; **высоту** можно менять под контент.
- Открытие — вероятно как попап поверх клавиатуры (как окно редактирования клавиши) или
  отдельная «страница». Уточнить — см. открытые вопросы.

## 4. Архитектура (главный принцип — уже проверен на редакторе клавиатуры)

**Общий движок + общий формат конфига. UI — нативный на каждой ОС.
UI-код между Swift (mac) и AHK (Windows) НЕ шарим — это тупик.**

Слои:
- **Правила** — `TYPOGRAPH.md` (общий спек).
- **Движок** — `Typograph.run` (mac) / AHK-порт (Windows) по тому же спеку. Не трогаем.
- **Настройки** — уже есть как `TypographSettings` в `Typograph.swift` (тумблеры групп
  G1–G7, ёфикатор, PercentSpace, CurrencyPosition). Нужно:
  1. Спроектировать секцию **`[Typograph]`** в `config.ini` (ключи/значения) — аккуратно,
     с оглядкой на Windows-совместимость, как делали формат раскладки.
  2. Читать/писать её через слой формата (по образцу `LayoutFormat`/`LayoutStore`).
  3. UI на маке (SwiftUI, в стиле нового редактора `KeyboardEditorView2`) правит эту секцию.
- **Пресеты** — именованные наборы значений (Базовый/Стандартный/Продвинутый) в коде;
  «Кастомный» = ручная правка, сохраняется в конфиг.

**Железное правило:** трогаем UI + слой настроек/формата. Сам типограф-движок и его правила —
НЕ переписываем (только читаем `TypographSettings`).

## 5. Открытые вопросы (решить в новом диалоге до кода)

1. **Предпросмотр:** где и как? Отдельная зона «до/после» на тестовом тексте? Свой текст
   пользователя? Обновление вживую при переключении правил?
2. **Форма окна:** попап поверх клавиатуры (как редактор клавиши) или полноэкранная «страница»
   редактора со сменой режима (раскладка ↔ типограф)?
3. **Матрица правил:** финальная группировка/оси (по эскизу — черновая). Сколько правил
   выносим в «простой» вид, сколько прячем под «Кастомный».
4. **Пресеты:** какие именно, что в каждый входит. Есть ли «Сам решай» (что это значит?).
5. **`[Typograph]` формат:** имена ключей, дефолты, поведение при отсутствии секции.
6. **Ёфикатор** — часть этого экрана или остаётся отдельным пунктом меню?

## 6. Порядок работы (предложение)

1. Договориться по открытым вопросам §5 (особенно предпросмотр и форма окна).
2. Спроектировать секцию `[Typograph]` (формат) + чтение/запись, покрыть тестами
   (по образцу `LayoutFormatTests`). Движок не трогаем.
3. Собрать статичный UI-скелет матрицы + пресетов рядом с редактором (ветка `typograph-ui`).
4. Подключить живые данные (чтение/запись настроек) + предпросмотр.
5. Ховер-подсказки с примерами.
6. Полировка по макету.
7. Windows — догоняет по этому же спеку и `[Typograph]`-секции (отдельная задача).

## 7. Полезные ориентиры в коде

- `Typograph.swift` — движок + `TypographSettings` (что вообще настраивается).
- `TYPOGRAPH.md` — правила (общий спек с Windows).
- `LayoutFormat.swift` / `LayoutStore.swift` — образец слоя «формат ⇄ файл» для секции `[Typograph]`.
- `KeyboardEditorView2.swift` — стиль/приёмы нового UI (тёмная тема, ховер, попап, плашки).
- `bad_typograph.pdf` (корень) — референс «как НЕ надо» (анти-паттерны).
- Эскиз нашего концепта — у автора (пресеты сверху + матрица справа, примеры в ховере).
